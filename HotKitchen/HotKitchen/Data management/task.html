Description

You have successfully built the foundation of the HotKitchen application. Users can register, sign in, manage their profiles, and staff can manage the menu. The final and most critical piece is allowing customers to place orders and staff to process them. This is where the application's core business logic comes to life.

In this final stage, you will implement the entire order management workflow. This includes creating a data model for orders, building endpoints for customers to place them, and providing restricted endpoints for staff to update their status.

This project was recently updated. If you started before the updates and are facing issues, check the end of the Stage 1 description for notes on the update.

Objectives

Your goal is to create the data structure and API endpoints necessary for a complete order system.

  • Create an Order Data Model: Define the structure for an Order.

  • Implement Order Placement: Create an endpoint for any authenticated user to submit a new order.

  • Implement Order Processing: Create a restricted endpoint for staff users to mark an order as complete.

  • Implement Order History: Create endpoints for users to view all past orders and all currently incomplete orders.

Order Data Model

You will need to create the Order data class to represent an order in the system.

  • orderId (integer) - The unique identifier for the order, generated by the server.

  • userEmail (string) - The email of the user who placed the order.

  • mealsIds (list of integers) - A list of meal IDs included in the order.

  • price (float) - The total price of all meals in the order, calculated by the server.

  • address (string) - The delivery address, fetched from the customer's user profile.

  • status (string) - The current status of the order. This will be either IN PROGRESS or COMPLETE.

API Endpoint Specifications

All endpoints require a valid Bearer token for authentication.

POST /order:

Creates a new order for the authenticated user.

  • Access Control: All authenticated users.

  • Request Body: A JSON array of integers representing the mealId(s) being ordered.

    [1, 2, 5]

  • Server-Side Logic: Upon receiving the request, the server is responsible for:

    • Validating that all requested mealId(s) exist.

    • Calculating the total price by summing the prices of the individual meals.

    • Fetching the userEmail and address from the authenticated user's profile.

    • Generating a unique orderId.

    • Setting the initial status to IN PROGRESS.

  • Successful Response (200 OK): Returns the fully constructed order object.

  • Failure (400 Bad Request): Occurs if any of the requested mealId(s) do not exist or if the user has not set up their profile (and thus has no address).

POST /order/{orderId}/markReady:

Updates the status of an existing order to COMPLETE.

  • Access Control: staff users only.

  • Path Parameter: The {orderId} of the order to be updated.

  • Successful Response (200 OK): Returns the updated order object with the new status.

  • Failure (Access Denied) (403 Forbidden): Occurs if a non-staff user attempts this action.

    {
    "status": "Access denied"
}

  • Failure (Not Found) (400 Bad Request): Occurs if no order with the specified orderId exists.

GET /orderHistory:

Retrieves a list of all orders made by all users.

  • Access Control: All authenticated users.

  • Successful Response (200 OK): Returns a JSON array of all order objects.

GET /orderIncomplete:

Retrieves a list of all orders that are still IN PROGRESS.

  • Access Control: All authenticated users.

  • Successful Response (200 OK): Returns a JSON array of all incomplete order objects.
